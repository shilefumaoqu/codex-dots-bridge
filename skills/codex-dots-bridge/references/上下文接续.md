# 上下文接续参考

用户在新对话给出旧 Codex 对话 ID 或链接并说“继续”“接着做”时，优先使用此流程。明确说“读一下”或“完整读取”时，继续按 Skill 中的全量快照契约读取；两种模式不互相替代。

仅在本机对话工具已启用 `local + read` 且当前调用方已发现对应工具时使用。Bridge 只读取指定 thread 的公开历史并保存派生状态，不需要 `send` 权限，也不恢复旧回合、工作目录、工具、授权或执行历史里提到的动作。历史提及的其他 ID 不扩展读取范围。若宿主已经向当前 Agent 提供可用记忆，可将其作为线索；Bridge 不读取或解析官方 memory 文件，记忆没有已核验的覆盖点时仍需扫描公开历史。

## 操作顺序

工具字段按当前 Skill schema：`codex_get_context` 必填 `request_id`、`thread_id`，可选 `mode`（默认 `continue`）、`refs`、`continuation_token`、`evidence_offset`、`delivery_cursor`、`wait_seconds`（0–20）；`evidence_offset` 仅用于单个 ref 的 `evidence` 请求。`codex_update_context` 必填 `operation_id`、`thread_id`、`expected_epoch`、`expected_revision`、`read_receipt_id`、`state`，可选 `processed_refs`。`codex_forget_context` 必填 `operation_id`、`thread_id`、`expected_epoch`、`expected_revision`。不要添加 schema 未定义的参数。

1. 调用 `codex_get_context`，默认 `mode=continue`。首次接续可能扫描全部可访问公开历史。
2. 对当前 source 批次沿原 `request_id` 查询 `pending`，用 `delivery_cursor` 取齐这份回执的全部页面。页面间不写状态；只有该批所有页面都收齐后才处理批次。若须用 `mode=evidence` 补读，也先取齐该回执所有页面。
3. 把本批内容合并到累计的 `task`、`requirements`、`completed`、`pending`、`execution`、`gaps` 六类数组；保留前批仍有效事实，把未核实事项写入 `gaps`。ref 由返回的 `thread_id/turn_id/item_id/fingerprint` 组成。单个 ref 可用 `evidence_offset` 续取截断正文。
4. 每批全部交付后，用该批的 `read_receipt_id` 调用一次 `codex_update_context`，传 `operation_id`、当前 `expected_epoch` / `expected_revision`、累计 `state` 和该批已交付并处理的 `processed_refs`。确认更新成功后才进入下一批。无需逐页面 update。服务端会拒绝未取齐页面或未接受 update 的续读，错误分别为 `continuation_requires_delivery`、`continuation_requires_update`。
5. 成功 update 后若此前读取回包给出了 `continuation_token`，再使用新的 `request_id` 发起后续 `continue` 请求。每一批都依次“取齐全部页面 → 合并累计状态 → 一次成功 update → 新请求续读”；不能先读取多批、最后才保存。要读取最新历史也须使用新请求；`delivery_cursor` 只分页当前回执。
6. 缺项、矛盾、索引不完整或关键状态仍未知时，继续用来源 ref 补查；无法补齐则保留 `gaps`。若续读被拒或发生超时/重启，先保留缺口，再用新请求核对，不把旧请求当成完成。
7. CAS 版本冲突后重新读取当前 revision 与状态，再获取绑定当前版本的新回执并重新整理；只合并已核验状态可用新的 `view` 回执，需要新来源时使用新 `continue` 回执。不要拿旧 `read_receipt_id` 直接重提。Bridge 校验结构、回执和 CAS，不判断语义是否正确，也不验证 `caller_correction` 确为用户表达。
8. 以后用 `mode=view` 只查看已保存状态；`view` 不刷新源历史。新工作的进展归实际新 thread；更新时 `consumer_thread_id` 必须等于目标 `thread_id`，`derived_from` 只记来源，不会选择另一分支。

`state` 必须含六个数组：`task`、`requirements`、`completed`、`pending`、`execution`、`gaps`；可选 `consumer_thread_id` 与 `derived_from`。每条事实含 `id`、`text`、`classification`（`reported`、`observed`、`inferred`、`caller_correction`）及 `source_refs`，还可带 `supersedes`。推断和调用方更正可不带引用，其他类别必须引用已交付来源。Bridge 接受已保存且仍有效的基础引用，以及本回执已交付的来源引用；版本冲突时重新读取、合并后再提交，不覆盖新版本。`codex_forget_context` 只清除 Bridge 派生状态，不删除源历史。

读取结果含 `request_id`、`thread_id`、`status`、`epoch`、`revision`、`state` 和 `owner_observation`；就绪后可带 `read_receipt_id`、`evidence`、`coverage`、`delivery_cursor`、`continuation_token` 与 `basis_valid`，错误时可带 `reason`。更新和删除回包给出 thread、epoch、revision 与状态；更新还返回 coverage。

## 覆盖与缺口

- `source_complete` 固定为 `false`，表示 Bridge 不声称取得完整源对话。`public_history_complete` 表示公开历史的投影扫描是否已覆盖；`public_projection_complete` 表示本次公开投影是否达到可复用的完整、稳定状态。
- 已知未打开的附件、压缩正文和未投影的结构化工具内容会保留在 `gaps`，并可能令 `limited=true`；`attachment_body_unavailable`、`compaction_body_unavailable`、`structured_tool_body_not_projected` 这些已知排除项本身不永久阻止后续 warm 复用。
- 关键范围未知、截断正文、未完成分页或源在读取期间变化属于阻断缺口，例如 `unfinished_turns_outside_index_unknown`、`item_text_truncated`、`pending_turns`、`source_changed_during_read`、`turn_changed_during_read`、`turn_changed_between_batches`、`continuation_turn_changed`、`observation_boundary_unverified`。不能把 `ready` 或 `continuous` 说成完整源历史；若缺口影响当前下一步，补查或明确保留阻塞状态。
- 可选 `resolved_gaps` 可记录稳定重扫后已解决的临时预算、流式观察或来源重建提示，例如资源预算耗尽、分页观察变化、来源身份/锚点重建。已知未读取的附件、压缩正文和未投影工具内容仍留在 `gaps`；warm 复用不会把这些源材料变为完整。
- `owner_observation` 的 `busy`、`idle`、`unknown` 均是带时间的观察，不是锁或发送授权；`unknown` 不等于空闲。
- forget 使用 `codex_forget_context`，按当前 epoch/revision 删除派生状态与回执正文并使迟到读取失效；它不删除源对话、官方记忆、旧完整读取快照或备份。

接口状态、版本和部署边界以当前发现的工具及 Bridge 运行版本为准。alpha.22 源码和隔离测试不证明运行服务、客户端工具目录或真实新对话已采用；效率也须在部署后按真实接续路径验收。完整读取与发送的精确合同见[任务工具参考](任务工具参考.md)。
