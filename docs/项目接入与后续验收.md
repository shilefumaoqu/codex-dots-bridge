# 可选扩展接入与后续验收

适用版本：0.2.0-alpha.4。本文讨论其他项目如何复用已安装的插件能力；插件的核心用法是 Codex 与 Dot 之间的任务协作，见[项目首页](../README.md)。

外部渠道属于可选扩展，不是插件内置功能或安装依赖。来源项目自行负责权限、消息接收和结果回传；未完成的实机验收单独记录。

## 接入顺序

现有项目接收用户请求 → 该项目的本机 Codex 对话 → 已安装的 dots_* MCP → 同一个 Dot → 原 task_id 的持久结果 → 来源项目按自己的授权回传。

桥接继续只提供 Codex MCP、配套 Skill 和维护 CLI。来源渠道消息接收与结果回传及其他项目自己的权限和数据存储由原项目负责，不需要为此给 Bridge 增加通用 REST API 或其他 Agent 安装器。此文是实施交接说明，不表示那些项目已经接通。

| 顺序 | 责任方与前提 | 产物 | 完成条件 |
| --- | --- | --- | --- |
| 1. 入口确认 | 来源项目确定用户授权的入口、目标和回传位置 | 一条真实来源请求及稳定 source_request_id | 能区分重复投递和新的用户意图 |
| 2. 本机检查 | 该项目 Codex 实际加载 Bridge Skill 与九个 caller 工具 | dots_status 的真实回包 | 服务可达、诊断可用，Tunnel 与订阅各自明确；不只检查配置文件 |
| 3. 保存关联 | 来源项目先保存提交意图、规范化正文及稳定键，再派单 | source_request_id → idempotency_key → task_id | 崩溃或回包丢失后仍可沿原键核对，不能靠新任务补偿 |
| 4. 一条自然任务 | 用户从正常入口指定一份无副作用文本任务 | 真实输入、Dot 结果、原任务证据 | 正文符合预先约定的交付标准；不是额外制造的后台测试 |
| 5. 原路回传 | 来源项目沿自己的发送授权取回和回传 | result_id 及发送/接收记录 | 结果入库、Codex 取回、接口接受、接收端实际收到、用户认可分别核对 |
| 6. 逐项扩大 | 一条自然闭环通过后，再增加澄清、更正、取消等样本 | 下表的实际证据 | 有未知执行状态先核对，不扩大重派或副作用权限 |

## 最低任务关联契约

- 业务幂等键由来源项目和稳定请求身份生成，1–128字符；同一个请求的相同内容始终复用同键。无法一次得到 task_id 时保留提交意图，按原键原文重试或查询，不能临时换键。用户改变需求用原任务 message；完成后的新工作用 followup。
- 记录来源项目、来源请求身份、任务 ID、input_revision、question_id、result_id 以及实际授权。logical_session_id 只是本项目逻辑标签，不能冒充来源渠道、Codex 或 ChatGPT 原生会话 ID。
- 任务正文明确目标、输入、交付标准及允许的外部动作。默认 safe_to_retry=false；只给文本授权就只处理文本。文件、命令、外部发送或业务写操作要由对应项目另外确认和验证。
- 等待每次最多20秒，当前回合默认总计五分钟。超时保留原任务；后续查询由来源项目已有的调度或用户主动请求承担，不在本桥接里另建常驻轮询器。
- waiting_input 时展示持久问题，真实答案用原 task_id、question_id 与稳定 message_key 提交；更正用新 message_key，不能把旧 question_id 当作可反复覆盖的槽。
- cancel_requested 只代表请求停止；cancelled 才是协作停止确认。reconciliation_required 必须先核对旧尝试和外部动作；没有回包不能证明没有执行。
- 读取并展示准确结果后，按原 result_id 记录 codex_received。发送接口回执不能代替接收端实际收到；上述事实都不能代替用户明确认可。来源项目有自己的回传去重键，建议绑定来源请求与 result_id，防止重复通知。
- 公开仓库和 Issue 只放脱敏样本；不复制 caller/worker/平台密钥、claim_token、真实正文、数据库或回调地址。

实际参数和类型见[工具契约](任务与工具契约.md)，不要根据本文生成另一套接口 schema。

## 定时回访是什么

| 机制 | 做什么 | 是否为当前使用必需 |
| --- | --- | --- |
| MCP Events | 新任务或续接通知 Dot 重新读取队列 | 当前已接通的派单路径 |
| Bridge 与 Tunnel 后台运行 | 保存任务并接收 Dot 的检查点、问题和结果 | 接收新结果时需要在线 |
| Codex 原对话定时回访 | Codex 官方自动化定期在原对话按 task_id 查进展，把新问题或终态告诉用户 | 可选；默认不开启 |

回访不负责让 Dot 执行，也不是外部消息回传服务。默认示例为15分钟一次、最长24小时，但实际创建要遵从用户指定的范围和截止时间；必须明确启用后才创建。状态不变保持安静，终态或截止后停用。电脑和桌面应用需要满足官方本地任务运行条件。若来源项目已经有合适的状态跟进和回传机制，可继续使用它，不必再开一份原对话回访。

精确提示词与官方入口要求见[回访说明](../skills/codex-dots-bridge/references/原对话回访.md)。开启和实际执行是不同证据，不能把保存调度配置记为回访成功。

## 留给接入后实际观察的清单

不要求为了凑时长继续等待。每项按真实发生时间补证据；此前本地自动化与19条真实合成任务的结果继续有效。

| 场景 | 最少需要保留的证据 | 判定 |
| --- | --- | --- |
| 来源项目自然任务 | 来源请求 → 原 task_id → result_id → 来源端实际回传 | 输入与结果匹配，接收端实际收到独立确认，无重复派单或回传 |
| 自然订阅续订 | 原订阅、refreshBefore、真实续订请求、后续任务 | 同一有效订阅自然刷新后仍能完成任务；不手改期限伪装自然续订 |
| 日常重开 Codex | 原任务 ID 与重开后的查询 | 仍是同一任务/结果；CLI新进程已验证，桌面整体重开待观察 |
| 跨日与休眠恢复 | 停机时段、恢复后任务/订阅/执行尝试 | 已保存结果不丢；未知云端执行状态明确待核对，无擅自重派 |
| 登录自启 | 用户选择启用后实际注销/登录 | 本实例后台在线，其他服务不受影响；未完成真实登录自启验收 |
| 用户认可 | 用户对具体 result_id 的明确评价 | 才能记录 user_accepted；不以默认值代填 |
| 外部文件或业务动作 | 明确授权、实际可访问输入、操作前后证据 | 单独验收；文本闭环不替代文件或业务操作成功 |
| 可选回访/恢复切换 | 仅在真实需要并获相应授权时执行 | 记录首次运行、去重、停用，或恢复后的同实例/同任务读回 |

故障先按[维护与故障排查](维护与故障排查.md)处理。本项目范围的准备已就绪，不因此向其他项目自动派任务或扩大其原有授权。
