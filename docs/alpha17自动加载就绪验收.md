# alpha.17 自动加载就绪验收

## 当前结论

截至 2026-10-12，`0.2.0-alpha.17` 已完成构建、隔离安装生命周期、本机原实例升级，以及一条未加载目标的真实 **Dot → 原对话 → Dot** 往返。它仍是未发布候选，没有 GitHub Release 下载资产。一次合成任务通过不代表所有桌面版本、账号、忙碌场景或长期运行通过。

本次确认的缺陷是桌面 Router 在一次发现请求开始时固定候选及 `canHandle` 响应；目标在该请求中途加载完成，不会重新检查已经否认的候选。候选只在明确 `native_owner_unavailable` 且尚未发送时导航一次；之后每次阴性查询结束，间隔 250ms 发起新查询，受原 60 秒投递预算与 abort 约束。单次查询本身可能约 10 秒，并非每 250ms 完成一次发现。取得新鲜状态后才允许一次发送，未知回执不重发。

## 机制对照

- 样本为新 CLI 合成的空对话；没有手动打开目标。
- 对同一目标只导航一次。第一次查询耗时 10.14 秒，返回 no-client；原桌面 role/success 日志出现在该次查询中间。
- 随后的新查询耗时 2.334 毫秒，发现 owner。
- Router 的私有发现只在发起时读取一次 `canHandle` 快照；角色变化后不会重评本次发起的查询。因此后续查询发现 owner，不能证明此前请求重新路由或可发送。
- 该对照包含一次导航和只读发现，没有发送聊天；它单独不能证明往返。后续真实验收见下文。

## 真实往返

第一项请求因 Dot 开始处理时五分钟试验期限已经结束，以诊断结果收尾：send/status 均为 0 次、没有原生回合。未恢复、续期或重发这项请求。先完成无发送的就绪控制检查，再执行批次内独立的第二项请求。

第二项使用正常新建的合成对话，无逐项登记。发送前只读发现明确返回无 owner，没有手动打开目标。随后Dot 实际采用当前任务、来源、规则和服务器期限，发送工具只调用一次，结果查询两次。原对话产生关联新回合，准确回复算术答案及唯一测试标记；原生数据库、回合回执和Dot 保存的结果三处匹配，`verification=exact_turn_reply`。Codex 已确认取回，没有代替用户记录认可。

## 忙碌补测与目录拒绝

在用户另行明确允许后，向同一合成测试对话提交一次纯文本长生成，准备真实忙碌样本；该准备不是 Dot 往返证据。Dot随后领取独立补测任务，采用 alpha.17 / v6 和当前服务器期限。其唯一一次发送工具尝试在宿主调用层被拒绝：`catalog changed after prepared`。沿原请求查询返回 `request_not_found`，本机没有该请求的发送占位。没有取得实际忙碌状态、选项或回复；任务以诊断结果结束，未重发，不判定忙碌测试通过。

故障之后只读取得本机生产 MCP 的 14 个工具三次，完整定义摘要一致。此证据仅覆盖故障后的本机采样，不能证明故障瞬间或云端工具目录没有变化，也不足以确认宿主内部根因。本轮未更改工具参数、规则、图标包或平台权限以尝试绕过拒绝；按首次关键失败停止本分支。

独立只读检查亦未发现可证实的 Bridge 动态目录缺陷：工具在连接 transport 前同步注册，没有运行时增删工具；SDK 的变更通知只有连接后才发送。后续需要宿主准备与拒绝时的目录 revision/摘要及请求审计，不能凭当前采样判定外部平台根因。
