# 发布与升级

`0.2.0-alpha.7` 是 Windows x64 预发布版本，通过单文件 Setup.exe 安装，内含 Node 运行时与生产依赖，同时保留可核验的 ZIP 构建载荷。安装、升级、卸载和真实连接的具体通过、失败或未验证项，以该版本 Release 验收记录为准。旧 alpha.4 不能代替本版本的能力和验收。

## 来源与发布资产

源码仓库为 [shilefumaoqu/codex-dots-bridge](https://github.com/shilefumaoqu/codex-dots-bridge)，下载入口为 [GitHub Releases](https://github.com/shilefumaoqu/codex-dots-bridge/releases)。访问范围以仓库当前可见性为准；如仓库为私有，需登录有访问权限的账号。以该版本 Release 中实际列出的资产与记录为准。

使用者应在正式 Release 核对版本、Setup/ZIP 及 SHA256 文件，不使用猜测的资产地址。源码、桥接运行程序与分发包需版本一致；使用者自己的私有插件连接属于独立配置，不分发开发者身份与凭据。

## 构建与发布顺序

1. 按公开文档白名单检查源码、链接、版本、秘密格式、第三方来源与许可；需要公开历史时另做明确范围的历史检查。
2. 类型检查、构建、测试与适用的官方 Codex 安装覆盖；记录真实结果及跳过项，不将未运行远端 CI 写为通过。
3. `scripts/package.ps1 -IncludeTunnel` 生成含锁定运行时、生产依赖与官方 Tunnel 的校验载荷。
4. 用 `scripts/build-setup.ps1 -Compiler 官方InnoSetup编译器路径` 将同批载荷构建为 Setup；可用 `-PackageRoot` 指向已校验载荷、`-OutputDirectory` 指定新输出目录，实际参数以脚本 help 为准。构建结果与安装生命周期须分别验收，不从其他版本猜 Setup 参数。
5. 在独立隔离目录与数据目录验收 Setup 的安装、重复安装、升级、冲突保护、卸载保留数据；再实际确认 MCP/Skill 加载、连接与新包文本闭环。
6. 完成本批差异审查及[发布门禁](发布门禁.md)，记录历史证据、新包证据和仍未验证项。
7. 准备具体仓库、commit、Tag、附件与 Prerelease 正文，由维护者明确授权发布后再 push、打 Tag 和创建 Release。当前工作不自动执行这些外部操作。

构建复用锁定 ZIP 载荷与许可材料，保留 Node/Tunnel 伴随许可。CI 或构建成功不会自动发布；正式上传后再核对实际下载、校验、版本与链接。

## 升级与回退

安装程序与用户数据分离，升级、卸载按保留任务、结果、配置及凭据的契约执行。具体版本和环境的真实验收结果以该版本 Release 记录为准。

1. 记录旧版本、安装位置和 data-dir；使用旧版 backup 创建受保护备份，保留旧安装材料。
2. 读取活跃任务，停止本实例并确认相关子进程退出。云端工作可能继续，未知任务不重派。
3. 用新版安装器升级程序，沿原 data-dir 更新本项目 owned 注册，不覆盖外来同名或用户修改的内容。冲突须保留并报告。
4. 新对话实际发现工具，调用 status/doctor，读回旧 task_id/result_id、revision、ACK 与订阅，再做一条独立无副作用文本任务。
5. 回退先停新版，移除其 owned 注册并保留数据，再用旧安装材料重新注册。未来数据库迁移可能影响降级，须按实际兼容说明或离线备份恢复，不能盲目覆盖。

现有 ZIP 路径升级时先停止旧实例，旧 uninstall 移除本项目注册并保留数据，新 `scripts/install.ps1 -DataDir 原数据目录` 重建。若 Codex 原生路径变化，按当前 CLI help 显式指定自己的安装路径，不猜旧路径；归属冲突不自动删除。

## 离线恢复

恢复限定同账号与同 Dot。所有相关源/目标实例先停止，恢复到空目标；备份含密钥，应受当前用户/SYSTEM ACL 保护。恢复保留 active 订阅与待投递事件，启动前核对工作区、Dot 与 callback 归属。恢复命令成功不等于任务回读成功，云端切换需要独立验收。详见[维护与故障排查](维护与故障排查.md)。
