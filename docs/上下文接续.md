# 对话上下文接续

本文说明本机 Bridge 源码候选中的上下文接续接口。源码候选暂为 `0.2.0-alpha.22`；运行 Bridge 未升级，云端工具目录和真实阿星新对话尚未验收。文档与 Skill 更新不代表这些入口已被运行服务或 Dot 采用。

## 适用范围

用户在新对话提供旧 Codex 对话 ID 或链接并说“继续”“接着做”等时，优先调用上下文接续流程。旧的“读一下”“读取上下文”以及明确要求完整读取的场景仍按[对话完整读取默认约定](对话完整读取默认约定.md)，继续使用 `codex_read_conversation` 与 `codex_conversation_status` 的固定快照和全块取齐契约。不能把全量快照的旧偏移量说成历史增量。

接续只读取指定本机 thread 的公开可访问历史并保存该 thread 的派生接手状态。历史中出现的其他 ID 不扩大范围。工具要求本机对话能力为 `local` 且 `read` 已启用；不要求 `send` 权限。新对话仍有自己的工具、工作目录和授权，旧对话的环境不会自动继承。若新对话当前能力不足以继续具体工作，应明确标记阻塞和缺失条件。

## 接手流程

1. 用 `codex_get_context` 的 `continue` 模式检查已保存状态并读取公开历史。Bridge 不读取或解析官方 memory 文件；若当前宿主已向 Agent 提供可用记忆，可将其作为查找线索。记忆覆盖点未知时，Bridge 仍须扫描可访问的公开历史，不能把记忆当作已核验水位。第一次没有可验证的覆盖基础时，读取器可能需要分页扫描全部可访问公开材料。
2. 处理 `pending` 时沿同一 `request_id` 查询，并用 `delivery_cursor` 取齐这一批回执的全部页面。页面之间只读不写；全部页面取齐后再处理这一批。若没有更多源材料但本批仍有截断或关键未知，先用 `evidence` 定向补读并取齐页面，或明确保留缺口。
3. 将本批证据合并进累计的六类状态：`task`、`requirements`、`completed`、`pending`、`execution`、`gaps`。保留前批仍有效的事实和引用；未知事项写入 `gaps`。当前 Agent 负责语义整理，Bridge 不调用额外模型或判断内容是否正确。
4. 对每批只调用一次 `codex_update_context`，提交累计状态、本批 `read_receipt_id`、预期 epoch/revision，以及本批已交付并处理的 `processed_refs`。确认更新成功后再继续源读取。服务端要求 continuation 前一批必须 `delivery_complete=true` 且 update 已接受；未满足时会返回 `continuation_requires_delivery` 或 `continuation_requires_update`。不需要逐页面提交更新。
5. 成功提交后，如果本批有 `continuation_token`，用新的 `request_id` 发起 `continue` 请求继续源读取。它与当前回执的 `delivery_cursor` 不同。每一批都重复“取齐页面、合并状态、成功更新”后再续读。超时、重启后的 `reconciliation_required` 或没有续读令牌的部分结果均保留缺口，用新请求核对；不能把旧请求当成最新。
6. 若 update 遇到 CAS 版本冲突，读取当前 epoch/revision 和状态，再按当前版本重新整理。先取得与当前版本绑定的新回执；仅合并已核验状态可用新的 `view` 回执，需要新证据时重新 `continue` 并取齐。不得用旧 `read_receipt_id` 直接重提。之后的新对话可用 `view` 查看状态；刷新源历史必须使用新请求。

历史材料可能包含用户更正和 Assistant 中途决定、进展；不能只读最终回复。对未终结轮次、最新要求、执行状态或关键事实仍有不确定性时，继续补查或把缺口列入 `gaps`，不能因六个数组有文字就声称接手完整。

## 工具参数与状态

`codex_get_context` 接受 `request_id`、`thread_id`，以及 `mode`（默认 `continue`，可选 `view` / `evidence`）、`refs`、`evidence_offset`、`continuation_token`、`delivery_cursor`、`wait_seconds`（0–20）。同一读取请求绑定固定参数；重复请求用于查询同一作业或取同一回执页面。取得最新历史需新建请求。`evidence_offset` 仅在 `mode=evidence` 且恰有一个 `ref` 时有效。

`codex_update_context` 接受 `operation_id`、`thread_id`、`expected_epoch`、`expected_revision`、`read_receipt_id`、`state` 和可选 `processed_refs`。每个事实含 `id`、`text`、`classification`（`reported` / `observed` / `inferred` / `caller_correction`）及 `source_refs`；推断和调用方更正可无引用，但其类别仍须准确。其他事实必须带引用。Bridge 接受已保存且仍有效的基础引用，以及当前回执已交付的引用；接口不能独立证明 `caller_correction` 确由用户表达，也不能把 `reported` 自动升级为已验证事实。并发版本冲突后重新读取、合并新证据再提交，不覆盖新版本。

`codex_forget_context` 接受 `operation_id`、`thread_id` 与预期 epoch/revision。它删除该 thread 的派生状态、回执正文及相关操作记录，提升 epoch 并使未完成读取和迟到回调失效。它不删除源对话、官方记忆、旧完整读取快照或既有备份。

新对话的后续进展属于实际新 thread。可选的 `consumer_thread_id` 必须等于更新目标 `thread_id`；`derived_from` 仅记录来源，不自动读取或选择另一分支。不要把新对话的工作结果写回旧源的接续记录。

读取回包的状态包括 `pending`、`ready`、`partial`、`reconciliation_required`、`failed`、`forgotten`。`ready` 只表示本次公开投影读取达到可复用条件，不证明模型已正确理解或完整处理。`coverage.source_complete` 固定为 `false`，不声称完整覆盖源对话；`public_history_complete` 表示公开历史的投影扫描是否已覆盖，`public_projection_complete` 表示本次公开投影是否达到可复用的完整、稳定状态。另检查 `fetched_refs`、`delivered_refs`、`processed_refs`、`delivery_complete`、`continuous`、`limited`、`gaps` 和可选 `resolved_gaps`。已解决的临时预算、流式观察或来源重建提示可列在 `resolved_gaps`；实际无法读取的附件正文、压缩正文或未投影结构化工具内容继续保留在 `gaps`，并不因 warm 复用而声称其源材料完整。

已知未读取附件正文、压缩正文或未投影的结构化工具正文会保留为 gap，并令 `limited=true`，但本身不永久阻止后续 warm 复用。关键范围未知、正文截断、读取分页不完整或观察期间源内容变化属于阻断缺口，必须补查或保留为未完成状态。临时预算、流式观察或来源重建提示只有在新的稳定扫描确认解决后才可进入 `resolved_gaps`；缺失的源正文仍留在 `gaps`。只有公开投影完整、当前批次页面已全部交付并处理、无阻断缺口且前序批次均已接受时，才能推进 `continuous`；这仍不代表整个源历史完整。历史任意旧内容改写当前无法完全检测，读取器明确报告 `historicalEditsDetectable=false`；发生身份变化、回滚或覆盖失效时应重建相关基础，不宣称捕获所有旧文改动。

`owner_observation` 是带 `observed_at` 的 `busy` / `idle` / `unknown` 观察。它不构成执行锁、授权或原对话控制能力；未知不得解释为空闲。接续读取不发送消息、不恢复回合、不导航桌面、不执行历史中提到的动作。

## 状态与验收边界

源码实现和隔离测试只能证明候选逻辑范围。运行 Bridge 仍为原版本，alpha.22 候选未部署；真实阿星新对话中的工具发现、首轮读取、自动补查、更新回执以及实际工作效率，均须部署后逐项验收。不得把单元测试、接口注册或文档更新描述为真实接续已跑通。
