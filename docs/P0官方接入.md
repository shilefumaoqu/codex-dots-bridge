# P0 官方接入与真实验收

更新：2026-10-09。**P0 已通过两条真实样本：echo 与用户回答 blue 后的同任务澄清续接。** Tunnel、私有插件、Events、Dot 结果入库和 Codex ACK 均有真实证据，见[P0 真实验收记录](P0真实验收记录.md)。本页保留复现步骤；完整产品及 P1–P4 尚未交付。

## 1. 前置权限与接入身份

- Platform Tunnel 创建/编辑者需 Tunnels **Read + Manage**；runtime key 的主体以及选择 Tunnel 的操作者需 **Read + Use**。普通项目 key 的存在不自动证明具备 Tunnel 权限。
- Tunnel 关联目标个人 Platform organization、ChatGPT workspace，以及实际需要调用的其他组织。workspace 自定义 MCP 插件权限独立于 Platform 权限。
- 本地仅运行无副作用探针。平台密钥只进入 Tunnel 的安全 env/file 引用，不写进仓库、示例、日志或 MCP 子进程；不得为了完成 P0 擅自创建 key 或公共插件。
- 用户在自己的目标 Dot 中订阅队列；“现有 Dot 能调用工具”与“正确 Dot 已订阅”分别核验，不从未公开的原生身份字段推断绑定。

来源：[官方 Tunnel 指南](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)、[官方权限说明](https://github.com/openai/tunnel-client/blob/v0.0.16/docs/permissions.md)、[Platform Tunnel 设置](https://platform.openai.com/settings/organization/tunnels)。

## 2. 初始化与本地端点

```powershell
.\scripts\dev.ps1 build
.\scripts\dev.ps1 test
.\scripts\dev.ps1 probe -- init
.\scripts\dev.ps1 probe -- run
```

命令与可选 `--data-dir` 的准确位置以 CLI help 为准。默认数据目录为 `%LOCALAPPDATA%\CodexDotsBridge\p0`；`init` 生成 `worker.key`、`caller.key`，均为不带 `Bearer ` 前缀的随机 hex 内容。

`run` 监听随机环回端口，并将实际 endpoint 写入数据目录的 `config.json`。Tunnel 指向 worker 路由 `/mcp/dot`；控制入口 `/control/:op` 使用 caller Bearer token。两种 token 不可互用。重启前后核对 endpoint，不能沿用已失效的随机端口。

`stdio` 用于 Codex 本地工具接入，与 Tunnel HTTP worker 路由职责不同；不把已连本地 stdio 算作云端 Dot 已连通。

## 3. 配置官方 Tunnel

从[官方 release](https://github.com/openai/tunnel-client/releases/latest)获取适合系统的整套发布包并保留伴随文件。配置按当前 binary help、`doctor --explain` 核验；下例只展示字段，替换实际路径和 endpoint 后使用：

固定验证版本为官方 Tunnel v0.0.16 Windows amd64；ZIP SHA256：edef7241b0c647fcb30f1a80ff376b6b25c51927960f257a3f01e21b17c2aba6。发布包应保留完整伴随文件与许可，不能仅复制客户端EXE。

```yaml
config_version: 1
control_plane:
  tunnel_id: tunnel_替换为真实完整ID
  api_key: file:C:/安全目录/tunnel-runtime.key
mcp:
  server_urls:
    - channel: main
      url: http://127.0.0.1:替换为config.json中的端口/mcp/dot
  extra_headers:
    X-Codex-Dots-Worker-Token: file:C:/数据目录/worker.key
health:
  listen_addr: 127.0.0.1:0
  url_file: C:/运行目录/tunnel-health.url
log:
  level: warn
  format: json
```

env/file 引用避免把 secret 写进配置和 argv。`mcp.extra_headers` 提供运行与 discovery/probe 的基础头；`discovery_extra_headers` 只在需要不同探针头时添加。连接器转发头最后覆盖静态头，因此服务端须校验专用 worker 头准确值，不能视为不可覆盖的注入。平台 runtime key 不替代本地 worker key。

先运行官方客户端的 doctor，再按 binary help 启动；分别观察 process、healthy、ready、polling。`doctor` 的 API key PASS 仅证明配置加载与引用可解析，不会向 OpenAI 控制面验证 Tunnel Read/Use；账号权限与可用性必须通过真实 runtime 连接及后续工具调用核验。任一层未成立都不能宣称工具调用可用。[固定 v0.0.16 配置与头优先级](https://github.com/openai/tunnel-client/blob/v0.0.16/docs/configuration.md)、[doctor 源码](https://github.com/openai/tunnel-client/blob/v0.0.16/cmd/client/doctor_command.go)。

本机 binary help 确认：前台使用 `run`；将来由 Codex 管理长期后台进程时，优先采用其官方 `runtimes connect` / `runtimes status` 管理入口，并分别核实 `process_running`、`healthy`、`ready`。这里只记录当前官方能力，不代表本项目 P2 安装器已实现。

在 [ChatGPT Plugins](https://chatgpt.com/plugins) 添加 custom MCP server，选择 **Tunnel** 和相同 tunnel ID。此方案用 Tunnel 的专用本地头，插件 Authentication 选择 **None** 的组合须真实核验。扫描后应看到任务工具及 Events；改变定义后 rescan。客户端必须保持运行。此路径是私有接入，不能直接用于公共插件提交。

## 4. MCP 现代请求与 SDK 扩展

使用 `createMcpHandler(factory, { legacy: 'reject' })`，Node 侧通过 `toNodeHandler` 转接。每请求创建 MCP 实例，持久任务/订阅放在实例外的存储。注册工具之外，以 `mcp.server.setRequestHandler(method, {params,result}, handler)` 实现 Events；handler 接收已验证 params。自定义 result 主动验证后返回，SDK 负责现代 wire 的 `resultType:"complete"`。

现代 HTTP 请求必须有：

```text
Content-Type: application/json
MCP-Protocol-Version: 2026-07-28
Mcp-Method: events/subscribe
X-Codex-Dots-Worker-Token: <worker.key 的实际内容>
```

```json
{
  "jsonrpc": "2.0", "id": 1, "method": "events/subscribe",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    },
    "name": "<events/list 返回的实际名称>",
    "arguments": {"queue": "<实际队列>"},
    "delivery": {
      "mode": "webhook", "url": "<ChatGPT 提供的 HTTPS 回调>",
      "secret": "whsec_<ChatGPT 提供的 base64 signing key>"
    },
    "cursor": null
  }
}
```

示例解释字段，不能自行伪造 ChatGPT callback/secret 代替真实订阅。`tools/call` 另需 `Mcp-Name` 等于工具名；events/* 不要求此头。现代 envelope 的 `clientInfo` 可提供但不是必须字段。

`server/discover` 原始响应须包含 `supportedVersions:["2026-07-28"]` 和根 `capabilities.events:{}`。SDK 2.3.1 没有内建 Events 类型，可用窄交叉类型传入根 capability；不可移到 `extensions` 代替。SDK client 的 discovery parser 可能剥掉未知根 events，所以验原始 wire 和插件 Events 列表，不能只验 SDK accessor。

来源：[SDK 现代协议说明](https://ts.sdk.modelcontextprotocol.io/v2/migration/support-2026-07-28)、[官方自定义方法示例](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/examples/custom-methods/server.ts)、[固定 server 2.3.1 声明](https://unpkg.com/@modelcontextprotocol/server@2.3.1/dist/createMcpHandler-D4NN8WsG.d.mts)、[固定 node 2.1.1 入口](https://unpkg.com/@modelcontextprotocol/node@2.1.1/dist/index.d.mts)。

## 5. Events 与 webhook 必须成立的字段

| 方法/消息 | 必须验证 |
| --- | --- |
| `events/list` | `events` 含稳定 name、description、`delivery:["webhook"]`、inputSchema、payloadSchema；可选 cursor/nextCursor 分页。 |
| `events/subscribe` | name/arguments 合法；delivery 有 HTTPS url 和合法 secret；可选 cursor、ttlMs；返回 id、refreshBefore、cursor、truncated。 |
| 订阅身份 | authenticated principal + callback URL + name + canonical arguments；重复订阅更新同一记录。默认 24 小时；省略 ttlMs 与显式 null 区分。 |
| Challenge | 先发送签名的 `{"type":"verification","challenge":"随机一次性短期值"}`；要求 2xx，回显恒时比较后才激活。失败返回 `-32015` 及 data.reason。 |
| 正式 event | eventId、name、ISO timestamp、data、cursor；data 符合 payloadSchema，应用数据不放顶层 type，整段 body≤256KiB。 |
| 签名 | Standard Webhooks；webhook-id 对应 eventId，webhook-timestamp 为签名时 Unix 秒，webhook-signature 与 X-MCP-Subscription-Id；序列化一次，签名/发送同字节。 |
| 重试与恢复 | 同 eventId、每次刷新签名时间，有限退避；410/413 不重试。订阅/outbox 跨重启保存，过期停止发送；secret 轮换有短双签窗口。 |
| `events/unsubscribe` | 按原 name/arguments/callback URL 匹配并授权，幂等停止；业务返回空对象。 |

secret 必须以 whsec_ 开头，base64 解码为24–64字节。callback 每次连接重新校验公共地址并连接到已验证 IP，保留 TLS hostname，拒绝私网/环回及重定向；challenge 同样执行这些检查。ChatGPT 仅支持 webhook 模式。P0 不重放历史，cursor:null；恢复靠持久任务查询。[官方 MCP Events 完整契约](https://developers.openai.com/plugins/build/mcp-events)。

## 6. 真机样本与证据链

P0 仅允许 **echo nonce** 和 **clarify blue/green** 两种固定无副作用样本；不得让探针触发发消息、发布、文件修改或其他外部动作。submit/answer/get/ack 的准确参数以 CLI help 为准。

| 顺序 | 验收证据 |
| --- | --- |
| 1 | 本地 build/test 结果，版本与数据目录；拒绝缺失/错误 worker 或 caller token。 |
| 2 | 官方 Tunnel doctor、运行、healthy/ready/polling；私有插件 discovery 原始响应及 Events 列表。 |
| 3 | 用户在目标 Dot 指定队列与领取规则；收到真实 subscribe、签名 challenge 成功、订阅持久入库。 |
| 4 | echo nonce 入库及 outbox；真实 webhook 2xx；目标 Dot 领取；完成工具提交准确 nonce 正文；get 可读取同一 task/attempt 的正文。 |
| 5 | clarify blue/green 领取后持久化澄清问题；用户经 answer 选择 blue/green；更新 revision 并触发事件；Dot 再领取，提交对应答案正文。 |
| 6 | evidence 导出上述 task/event/subscription/attempt/revision 的关联记录；结果入库、get 与 ack 分别可辨，不含密钥或完整签名 secret。 |

通过标准：两条真实样本都完整走通，输入/问题/回答/结果可以用稳定 ID 串联，且没有未解释的重复领取或重复提交。无法核实目标 Dot、正文缺失、challenge/签名/Events 不通，均判为未通过并保留阻塞原因。

协议模拟、Tunnel ready、event 2xx、Dot 自述完成、工具 accepted 或空 turns，均不能替代上述业务闭环。P0 至少核验订阅/任务重启后恢复；24小时自然续订和72小时真实稳定性另属后续验收，未观察前不能宣称完成。

```powershell
.\scripts\dev.ps1 probe -- status
.\scripts\dev.ps1 probe -- evidence
```
