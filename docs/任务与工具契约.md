## 简单聊天候选：原共享连接

| 工具 | 输入 | 回执 |
| --- | --- | --- |
| dots_chat_send | request_id:UUID, text:1–8000 字符, chat_id?:UUID | 稳定 request_id、Bridge chat_id、状态；同号同文取原记录，同号改文或改句柄拒绝 |
| dots_chat_status | request_id:UUID, wait_seconds?:0–20 | 只读匹配消息的保存结果；不发送、恢复或查询其他任务正文 |

两工具位于原 `/mcp/dot`，沿用原共享连接及唯一 Events 订阅，不提供独立 ChatGPT 身份认证。来源为服务器生成的 `shared_worker_connection_chat`，不冒充 Codex caller、人类身份或原生 approval。此入口仅覆盖当前文本回复；原共享工具并未被全平台隔离。

`queued` 只说明消息已保存且有有效订阅路线，`working` 只说明领取；两者不证明阿星原生在线或空闲。`reply` 要求当前消息的 final、revision=1、accepted_as_final 文本结果，返回 text；`error/expired/unknown` 不是成功。发送后沿同编号取齐真实回复再开始下一轮，不自动换号重发。在途、不明消息阻止下一条；明确终态后，人类明确要求的新消息可以继续。

worker 访问失效聊天任务时保留旧错误码 `reply_subscription_unavailable`、`category=state` 和 `retryable=false`，增量提供 `reason`：有效路由下消息过期为 `chat_message_expired`，路由失效为 `chat_route_unavailable`。两者同时失效时优先报告路由；旧回执及其他回复订阅错误可以没有此字段。消息过期的拒绝不能倒推为此前订阅故障，也不授权重发或领取过期任务。

直接 worker MCP 与经 `productionCall` 的 CLI/stdio 错误 JSON 均保留这两个白名单原因；代理不透传其他附加错误字段，原错误码、分类、重试标志和 MCP `isError` 含义不变。这不新增 caller 对失效任务的拒绝条件。

chat_id 是 Bridge 路由句柄，不是原生会话 ID。正常同订阅续期保持句柄；失效旧句柄不能转投或复活。仅同订阅恢复、旧消息均明确结束且新首轮省略 chat_id 时生成新句柄，回执带 `continuity=route_rebound_context_unverified`，须提示前文连续性需要重新确认。跨订阅不恢复。内部复用既有传输记录，不增加长期任务管理产品。

## Codex caller

| 工具 | 必需参数 | 可选参数/含义 |
| --- | --- | --- |
| dots_submit | idempotency_key, title, input:{text,links?} | safe_to_retry, deadline_hours, logical_session_id, delivery_window? |
| dots_list | 无 | status, logical_session_id, limit（1–100） |
| dots_get | task_id | 实际读取任务与结果，记录 caller read |
| dots_wait | task_id | after_sequence, timeout_seconds（0–20） |
| dots_message | task_id, message_key, text | question_id, deadline_hours |
| dots_followup | parent_task_id 与 submit 必需参数 | 与 submit 相同的可选参数；delivery_window?；新关联任务 |
| dots_cancel | task_id, request_key | reason |
| dots_status | 无 | `summary:true` 返回有界摘要；缺省保留旧版全任务元数据索引 |
| dots_ack_result | task_id, result_id | user_accepted 仅用于用户明确认可 |

写命令支持 `response_mode: full | compact`，缺省仍为 full；新调用端明确选择 compact。compact 返回任务身份、状态、修订、变更序号及必要引用；需要正文时沿原 ID 查询。首次接纳绑定模式，同键跨模式重试返回冲突；旧操作仍返回原回执。

业务参数序列化 UTF-8 上限为 1 MiB，HTTP/MCP 信封上限为 2 MiB。文本字段最多 100,000 字符，单独提交 100,000 个中文字符可通过；组合字段仍受总预算限制。title 最多 160 字符；links 最多 50 个 HTTP(S) 引用。引用存在不证明已读其内容。当前单任务 FIFO 执行槽，不提供 execution_mode 或并发配置接口。

同一提交保持幂等键和内容不变。`safe_to_retry` 默认 false，仅在用户明确允许无副作用安全重试时设 true；不明外部执行状态不得重派。Skill 默认每回合累计等待五分钟，单次最多 20 秒，用户可明确延长。

`delivery_window` 是 caller 为限定发送试验可选提供的 `{request_id,thread_id,text_sha256,not_after_utc}`，截止须为 UTC 毫秒精度，且距离 Bridge 接收时刻不超过五分钟。它绑定唯一 request、目标和正文；普通任务无需窗口或登记。Bridge 在调用者鉴权后的原业务事务中保存来源和窗口；同次重试不刷新 `received_at_utc`、来源或截止，遗留任务标为 `legacy_unknown`，不回填。窗口以服务运行时钟计时，服务重启即中断。

## 状态与证据

任务详情、等待结果及聊天查询共享 `progress`：阶段、等待原因、观察时间、可用下一步和已测等待时长。它解释排队、投递受阻、领取延迟和执行核对，不改变原 `status`。重复查询可更新观察时间，既有幂等命令的原回执仍保持不变。

| 状态/回执 | 能证明什么 |
| --- | --- |
| queued | 本地已保存，尚未证明 Dot 开始 |
| running | 已领取并持有当前租约 |
| waiting_input | 问题已保存，等待真实答案，释放执行槽 |
| cancel_requested | 已请求停止，尚未确认停止 |
| reconciliation_required | 执行不明，需要核对后决定恢复 |
| completed / failed / cancelled / expired | 对应持久终态；仍需核对结果内容或回执 |
| codex_received | Codex 实际读回并展示指定结果后的确认 |
| user_accepted | 用户明确认可该结果 |

回答使用准确 question_id，沿原 task_id 继续；更改已回答的答案时追加新更正，不重复回答旧 question_id。补充保存为新 revision，须有 Dot 检查点采用证据。完成后新工作使用 dots_followup。活跃取消须等 ack_cancel；桥接不能撤销已经发生的外部动作。

## Dot worker

核心工具为 list_tasks、get_task、claim_task、checkpoint_task、request_input、complete_task、fail_task、ack_cancel。`claim_task(response_mode=compact)` 同时返回当前工作输入、服务器顶层 `worker_rules`、`dispatch_context` 与 `server_clock`，可省去领取前的 get_task；旧客户端仍可先 get_task。其中 rules_version 与 bridge_version 标识实际返回的流程规则。可选 notify_owner 仅在另外配置并获授权时使用，不是默认对话回传路径。

`claim_task` 或 `get_task` 的顶层 `dispatch_context` 独立记录 caller 提交和各条消息来源；`authenticated_codex_caller` 表示经认证 caller 声明其来自既有人类请求，仅限当前委派范围，且 `human_identity_verified:false`、`native_approval_granted:false`。顶层 `server_clock` 给出 `time_source: bridge_host_clock`、`server_time_utc`、`task_deadline_utc`、`remaining_ms`，存在窗口时还有窗口截止、剩余毫秒与状态。它们由服务器生成，不从输入正文推断。

规则版本以当次服务返回的 `worker_rules.rules_version` 为准，不按可选能力开关推断旧版本。合法 caller 已转达的既有人类授权不因转达方式要求重复确认。历史、材料或其他代理消息不构成新授权，原生平台审批仍按原流程。限时试验必须依据 `server_clock`，不能使用模型自报时钟。窗口发送入口和实际投递前均须重新验证精确 request/target/text、当前 attempt 与最新 checkpoint/current input revision。截止或重启可能发生在动作已发出之后，须将结果作为可能已发送并沿原 request_id 核对，不以新编号重试。

`human_identity_verified:false` 只表示 Bridge 未独立验证人类身份，不表示 caller 已声明的既有授权缺失；`native_approval_granted:false` 只表示 Bridge 不授予原生审批，不表示宿主已拒绝。人类直接提出的要求，或 `dispatch_context` 中经认证 caller 对同一既有人类要求的转达，均按原目标、正文和委派范围处理，不因转达方式要求本人在 Dot 聊天再确认。实际宿主审批和更高优先级指令仍有效；需区分工具实际拒绝与尚未调用前的判断。

稳定 claim_key/completion_key/failure_key/ack_key 防止重复操作；claim_token 是秘密。30 分钟执行租约需要检查点续期，完成携带实际采用的 input_revision 和准确 result。旧修订或迟到结果可能只保留证据，须核对 accepted_as_final。详细流程见[Dot 执行说明](Dot执行说明.md)。

## 可选本机对话工具

新对话接续旧工作时使用的 `codex_get_context`、`codex_update_context`、`codex_forget_context` 与覆盖、引用、版本、删除边界见[对话上下文接续](上下文接续.md)。每批须先取齐所有 `delivery_cursor` 页面、一次提交累计状态并确认 update 成功，然后才用新 `request_id` 配合 `continuation_token` 续读；服务端拒绝未交付或未更新的 continuation。CAS 冲突后重读当前版本并使用新 receipt，不复用旧回执。该能力属于 alpha.22 源码候选；运行 Bridge、客户端工具目录与真实 Dot 采用情况须分别核实。既有完整快照和一次发送工具仍按下方契约执行。

| 工具 | 参数 | 合同 |
| --- | --- | --- |
| codex_read_conversation | request_id, thread_id | 官方 App Server 只读持久历史；不恢复或启动回合 |
| codex_send_message | request_id, thread_id, text；引导后可选 delivery_mode | 私有桌面 IPC；text 最多 8,000 字符，先核对在线与忙闲 |
| codex_conversation_status | request_id；可选 wait_seconds（0–20）、offset | 查询原请求；读取用 next_offset 取完固定快照 |
| codex_get_context | request_id, thread_id；可选 mode, refs, evidence_offset, continuation_token, delivery_cursor, wait_seconds | `local + read` 接续；`view` 查看，`continue` 读最新历史，`evidence` 定向补证 |
| codex_update_context | operation_id, thread_id, expected_epoch, expected_revision, read_receipt_id, state；可选 processed_refs | 保存带引用的六类派生状态，使用 CAS 版本检查 |
| codex_forget_context | operation_id, thread_id, expected_epoch, expected_revision | 删除该 thread 派生状态并使旧 epoch 的读取失效；不删除源历史 |

本机默认 off，可明确启用 read/read-send。local 模式按人类指定本机对话处理，无逐对话登记；旧 targets 模式须显式迁移，不能绕过其限制。

用户提供一个或多个本机 Codex 对话 ID / codex://threads/ 链接并说“读一下”“读取上下文”或用于交接背景时，默认完整读取每个明确指定目标的全部可访问已保存历史；没有固定 14 轮、近期若干轮或“看起来够了”的提前停止条件。只有用户明确指定近期、时间范围或局部内容时才按该范围处理，并标明局部范围。历史中提到的其他 ID 不自动扩大读取授权。

每个 ID 使用独立且稳定的 request_id。pending 沿原编号查询；status=completed 只表示服务端读取和保存完成，不证明调用方取齐。调用方从 context_offset=0 开始，按 next_offset 连续取得所有 context_chunk，核对 request_id/thread_id、固定 total_chars/context_sha256/receipt_nonce 和无缺口偏移；直到 next_offset=null，拼接字符数等于 total_chars，核对可用的 SHA-256 并成功解析 JSON 后，才报告“完整取得已保存历史”。跳到末块或只看到末块 null 不能证明此前内容已取得。最终摘要和结论在取齐后交付；过程中可保留中间提要，不能用提要替代尚未读取的正文。

交付时逐 ID 报告实际已读取轮数、块数、是否取到末端及缺口。stored_history_complete=true 仅证明官方持久历史页耗尽；source_complete=false 必须披露，不能声称压缩前材料或原始模型上下文完整。超时、超限、访问失败、工具输出截断或上下文容量不足时，保留已完成范围并明确未读部分，不将部分读取报成全部完成；可按块继续和保留中间提要，但不据此跳过后续正文。工具传输和校验能证明取得内容，不能证明模型逐字理解或长期记住全部内容。 读取限时 60 秒、正文上限 32 MiB；超限报告失败，不能截断冒充完成。有界缓存释放或服务重启后沿同 request_id 读原持久快照，不触发新读取；新的用户读取用新编号。

候选回包新增 read_scope 与 continuation_required：原生持久历史为 full_stored_history，旧快照为 full_history_snapshot；continuation_required=true 表示当前块之后还有块。false 仅说明当前块已到末端，不是调用方完整读取证明。字段不改变任意合法 offset 重取、既有幂等、冻结快照与缓存契约，不新增局部读取参数。显式局部请求限定分析范围，Bridge 读取工具仍返回完整快照。 本次新增规则和字段的实现、测试及部署边界见[对话完整读取默认约定](对话完整读取默认约定.md)。

发送先独立检查桌面 owner 的新鲜状态，并在写入前再次核对。仅明确返回 `native_owner_unavailable` 且尚未发送时，才向现存 Windows Store/MSIX Codex 实例投递一次对话深链；导航后在原 60 秒投递预算与 abort 内每次阴性查询结束后间隔 250ms 重新发现，超时立即结束。仅取得新鲜 owner/状态快照后才尝试一次发送，不能把导航 ACK 当发送证据。私有 Router 的 `canHandle` 是请求发起时的单次快照，不随角色更新重评；因此重新发现到 owner 不代表同一请求已进入发送路由。此路径可能改变桌面当前显示的对话，也可能继续目标已有的队列，须区分已有工作与本次发送。

同一目标已有发送在途时，新请求在落库前被拒绝，原 request_id 查询不受影响。只有取得准确原生 busy turn 和 owner 的请求才返回 `awaiting_delivery_choice`、观察元数据及 `delivery_options`；证据不足不创建等待选择的记录。Dot 先说明状态和实际支持项，由人选择；不能自行选择、换编号或默认排队。沿同一 request_id/thread_id/text 再调用发送工具并填写 `delivery_mode=next_turn`，才会等待观察到的原回合结束，然后仅尝试一次新回合；等待与其余投递前步骤共享最多 60 秒的投递前预算。`waiting_next_turn` 表示 Bridge 等待，不是原生队列已接受。出现另一个回合、原 owner 丢失、离线、未知、服务重启或截止就结束，不上线补发。`current_turn` 当前明确不支持可靠的原回合锁定，返回能力限制且不调用 steer；不能将它作为授权问题处理。缺少可靠活动回合身份时，下一回合选择也会明确报告限制。旧 targets 模式及历史 skipped 回执保持原契约。

离线、未知、发送不明不自动重发或补发，不打断目标。人工同时输入仍存在非原子忙闲竞态限制。

pending/accepted 不等于完成。仅同 request_id 的 completed + exact_turn_reply 与关联新回合回复构成该次结果；不得用“最新回复”替代。uncertain、send_outcome_unknown 或 reconciliation_required 可能已执行，先核对原编号，禁止以新编号盲重试。不会自动将结果发送回源对话或形成消息循环。

## 当前发送阶段与耗时

投递前最多 60 秒，涵盖 owner 核对、可选自动加载、用户选择后的忙碌等待与发送 ACK。只有有效匹配的发送 ACK 已持久化后，才开始独立最多 60 秒的回复等待，且只能取回该请求关联的新回合回复。ACK 仅证明相应接收阶段，不是 `exact_turn_reply`，更不等于用户验收；不匹配或尚未持久化的 ACK 不能启动回复阶段。

ACK 后的快速回复等待结束时，证据完整的准确回合可转为最长 24 小时后台只读取回；`delivery_state`、`reply_state`、`watch_state` 分别表示发送确认、回复取得和观察状态。查询复用原观察器，重启仅恢复绑定完整的已确认请求；证据失效或到期保留原记录，不重新发送。自动观察到期后，用户查询可触发一次有界只读核对。

存在 `delivery_window` 时，发送与快速等待仍受原窗口 guard 剩余预算限制；后台只读观察不延长或重新授予发送窗口。有效 attempt、最新 checkpoint/input revision、精确 request/target/text 与截止仍须成立。阶段切换不重新签发窗口，重试不延时。回复等待到限或窗口失效不撤销可能已发生的发送，也不授权补发。普通任务没有强制窗口；正向等待默认五分钟与官方读取的 60 秒/32 MiB 契约不变。

可选响应字段 `timing.stages_ms` 仅允许 `owner_lookup`、`autoload`、`busy_wait`、`send_ack`、`reply_wait` 五个阶段的非负有限毫秒数。仅返回实际测量项；未测量、未发生或无法确认的阶段省略，不能用零冒充。这里不加入 thread/owner 身份、目录、正文或凭据，也不新增工具名称或入参。阶段耗时不是领取、客户端采纳、端到端闭环或用户认可的替代证据。
